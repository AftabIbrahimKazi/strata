## Recurring technical gotchas (carried forward + new this session)

- **The docs site is not an npm workspace of the root package** (`package.json`'s `workspaces` only lists `packages/*`) — it installs `strata-css` from the **published registry**. A fix to `src/layers/base.js` (or any root-package file) does **not** reach the live docs site until a new version is published and the site's dependency is bumped/reinstalled. When a bug traces back to the core package, fix it at the source *and* add a local override/workaround in the docs site so the live site is actually fixed now — don't assume the source fix alone is sufficient.
- **A raw `curl`/`200` check on a third-party SVG-badge URL is not proof it will render through GitHub's camo proxy.** Happened twice in the profile-README side-work: two different services returned valid SVG directly but still showed broken in GitHub's rendered page. If a badge/image breaks on GitHub specifically, don't just re-verify the raw URL — swap to a host with a track record on that exact page (shields.io, in this case, since other badges in the same file already worked).
- **CSS variable tokens that are only "one shade" apart from each other (e.g. `--st-bg` vs `--st-bg-secondary`) can be individually "correct" (using the right variable) while still visually reading as broken** — the dark/dim `--st-bg-secondary` bug wasn't a wiring mistake, the token itself was just barely distinguishable from `--st-bg`. When a user says a themed surface "still looks black/wrong," check the actual token *values* in `variables.css`, not just whether the right variable name is being referenced.
- **A framework-level CSS reset gap can hide behind a component-specific symptom.** The "black text in the search dropdown" bug looked component-specific but was actually `strata-css`'s own `button` reset missing `color: inherit` — worth checking whether a "one weird element" bug is actually a base-layer gap before patching only the one visible symptom.
- **Prefer a real headless-browser measurement over static-code guessing for layout bugs** ("is the UI responsive" → wrote an actual Playwright audit across every route/viewport rather than grepping for suspicious class names) — found the *real* two root causes this way, both of which a static audit would likely have either missed or over-flagged with false positives.
- **`npx playwright install chromium` binary was already cached locally from a prior session** (`~/AppData/Local/ms-playwright/`) — worth checking before assuming a fresh browser download is needed (network-dependent, slower).
