## What shipped this session (in order)

1. **Core framework bug found and fixed: `shadow-sm`/`shadow-lg` silently applied the wrong shadow.** While enriching the docs site's Shadows page, `shadow-sm`, `shadow`, and `shadow-lg` all rendered the *same* box-shadow. Root cause in `src/registry/registry.js`: the responsive shadow loop registered class names as `shadow-${bp}` for every breakpoint in `BP_KEYS` (`sm`, `md`, `lg`, `xl`, `xxl`) — and since `sm`/`lg` are also the named-scale's own suffixes, that collided character-for-character with the base `shadow-sm`/`shadow-lg` classes. Registration is last-write-wins (`Map.set`), and the responsive loop runs later in the file, so it silently overwrote both. Fixed by dropping the undocumented bare `shadow-${bp}` case entirely (the documented `shadow-{bp}-{variant}` pattern — `shadow-md-sm`, `shadow-lg-lg` — was unaffected). **Verified via computed `box-shadow` in-browser**, not just reading the generated CSS. Pushed through the full pipeline: `dev` (`c85f901`) → PR #224 → `test` → PR #223 (also carried a pre-existing unrelated `test`→`beta` promotion that was already pending) → `beta` → PR #225 → `main`, confirmed present on `main` via `git show origin/main:src/registry/registry.js`. Version bumped to `1.8.16`, `CHANGELOG.md` entry added. **Not yet `npm publish`ed** — that's on the user.
2. **A second real framework bug found but NOT fixed — flagging for a future session.** `bg-opacity-*`, `text-opacity-*`, and `border-opacity-*` (5+5+4 = 14 classes) each set a CSS custom property (`--st-bg-opacity`, `--st-text-opacity`, `--st-border-opacity`) that is **never read back anywhere** in `src/registry/registry.js` or `src/layers/base.js` — grepped for consumers, found zero. Every one of these classes compiles, applies to the element, and has zero visible effect. This is documented prominently (with a live "click it, watch nothing happen" demo) on the Colors, Typography, and Borders docs pages, but the underlying framework bug itself is still present in `main` — only documented, not fixed. Worth a proper fix (either wire the opacity vars into the actual color functions via `color-mix()`, or remove the dead classes) in a future session.

## Recurring technical gotchas (carried forward + new this session)

- **`npm run build`, never `next build` directly** (`prebuild`/`predev` hooks regenerate `styles/strata.output.css`).
- **Verify CLI/framework behavior by reading the actual source, never assume** — this pattern found a real, shipped, undocumented framework bug this session (item 1 above). Don't trust `CLAUDE.md`/`README.md` prose as ground truth for *current* behavior; grep the registry and check the generated CSS output.
- **JIT scanner only reads literal strings inside `class`/`className` attributes** (`CLASS_ATTR_PATTERN` in `src/scanner/scanner.js`). Classes passed through a component prop like `<Playground classes={[...]}>` are **not** scanned, even though they're real string literals in the file — they need explicit `safelist` entries in `strata.config.js`. This bit every dedicated utilities page this session; the fix each time was adding the exact class list to `strata.config.js`'s `safelist`, verified via `grep` on the generated `strata.output.css`.
- **Don't trust a demo just because the class technically applies correctly.** Two categories of bug this session: (a) a class emits *wrong* CSS due to a registration collision (the shadow bug) — only caught by comparing computed styles, not by checking the class exists; (b) a class emits *correct* CSS but the demo context is wrong (`position-fixed` escaping a shared preview box, `translate-middle` without its assumed parent) — only caught by actually clicking through demos and checking layout, not by reading source. Both required going past "does the CSS rule exist" into "does clicking this actually produce the right/expected visual result."
- **Verification workflow (repeated 20+ times this session)**: build → `npm i -D playwright --no-save` (temporary, always removed after) → `npx next start` on a scratch port → screenshot/interact via a throwaway script → clean up (`rm` the script, `npm rm playwright`, kill the port by PID via `netstat`/`taskkill` on Windows — plain `pkill -f "next start"` sometimes leaves the process alive, confirmed by a stale-server false-negative mid-session; killing by PID is reliable).

Correct behavior to preserve going forward, not a bug to work around.
